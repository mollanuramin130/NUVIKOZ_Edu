## PHASE 2 — APPLY NEW OWNER-CONFIRMED DEMO POLICY

### 2.1 Zero File Uploads in Demo Mode

This is a mandatory and non-negotiable requirement.

**DEMO USER FILE UPLOAD LIMIT = ZERO.**

All Demo School accounts must be prevented from uploading user-supplied files.

This includes:

- Student photographs
- Admission documents
- Birth certificates
- Transfer certificates
- Homework attachments
- Assignment submissions
- School logos
- Teacher documents
- Images
- PDF files
- CSV or Excel files
- Payment screenshots
- Any other user-provided file

Do not create exceptions for privileged Demo users.

The rule applies to every interface:

- Next.js web application
- Flutter mobile application
- Laravel REST API
- Background jobs
- Import endpoints
- Any future client application

A disabled Upload button alone is insufficient.

Implement server-side authorization and upload restrictions.

The backend must reject unauthorized file uploads even when a user bypasses the frontend and sends requests directly to the API.

Apply restrictions to multipart uploads, file imports, base64 file payloads, remote-file ingestion, and equivalent attachment mechanisms.

### 2.2 Keep Demo Fully Interactive for Non-File Activities

Demo users must still be able to explore the software and create ordinary application records.

Allow authorized Demo operations such as:

- Student profile creation
- Class and section management
- Academic sessions
- Subject management
- Attendance entry
- Homework creation
- Homework Done marking
- Examination and marks entry
- Notice creation and approval simulation
- Timetable creation
- Teacher assignment
- Reports and dashboards
- Fee-record demonstrations

Use realistic workflows without requiring file uploads.

Apply configurable limits to Demo-created records, requests, report generation, and database consumption to prevent abuse.

Do not confuse zero file uploads with zero database usage.

### 2.3 Shared Read-Only Sample Document Library

Create a reusable library of preloaded demonstration documents.

Provide examples such as:

- Sample Birth Certificate
- Sample Admission Document
- Sample Report Card
- Sample Assignment
- Sample Payment Receipt

The documents must be clearly marked **SAMPLE / DEMO**.

Demo users may preview authorized sample documents, but cannot replace, modify, or upload new versions.

Avoid creating duplicate physical copies of identical sample files for every Demo tenant.

Use shared, controlled, read-only sample assets with safe URLs and access policies.

Avoid generating a new physical PDF for every preview when a shared static template or lightweight preview can meet the requirement.

## PHASE 3 — FINALIZE FREE LIVE PDF AND FILE POLICIES

### 3.1 Free Live School — Confirmed Limits

Use these exact initial defaults:

- Maximum PDF size: **5 MB per PDF**
- Maximum active uploaded PDFs: **50 per school**
- Maximum new PDF uploads: **10 per school per day**
- Total school file storage: **500 MB**
- Storage warning threshold: **80%**
- New uploads blocked at: **100%**

All limits must apply together.

If a school reaches any applicable limit, further uploads must be rejected.

Preserve previously uploaded documents and authorized read access.

For quota enforcement, count retained physical file versions until they are actually removed under an approved retention policy.

Define active-file count separately from physical retained-version storage so deletion, replacement, or versioning cannot silently bypass storage restrictions.

Use server-derived school-local dates for daily limits.

Prevent concurrent requests from exceeding quotas through transactional reservations and safe accounting.

### 3.2 Paid Live School — Configurable Limits

Paid School limits must be adjustable through Super Admin settings.

Support:

- Maximum PDF size
- Maximum PDF count
- Daily PDF upload allowance
- Total storage quota
- School-specific overrides
- Versioned policies
- Audit logs
- Storage usage reports

Do not hardcode paid storage allowances or require a paid third-party storage service.

Super Admin must be able to configure the plan or an individual school without changing application source code.

### 3.3 Feature-Specific Restrictions

Student homework file uploads remain disabled in the initial release, including Paid Live schools.

Students may view homework and mark it Done according to existing policy.

Teacher-created assignments and other permitted document workflows must obey their respective feature permissions, entitlement rules, and upload limits.

The new Free Live PDF policy does not automatically enable previously disabled upload features.

### 3.4 PDF Preview, Sharing, and Downloads

Apply authorization to all private PDF downloads and previews.

Use:

- Tenant-aware authorization
- Resource ownership checks
- Appropriate download rate limits
- Non-public document storage
- Safe content-disposition headers
- Audit logging for sensitive operations
- Storage and bandwidth monitoring

Prevent one school from accessing another school's documents.

Do not expose private student documents through public file URLs.

### 3.5 System-Generated PDFs

Separately control:

- Report card generation
- Receipts
- Student ID cards
- Certificates
- Other generated PDFs

A system-generated document must not automatically consume the user-upload PDF count.

However, every physically stored generated document must still be accounted for in the global physical storage budget.

Use cached templates, bounded generation, and on-demand rendering where appropriate.

Avoid uncontrolled PDF-generation loops.
