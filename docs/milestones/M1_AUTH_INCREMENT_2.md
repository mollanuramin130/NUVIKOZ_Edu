# M1 increment 2 — Browser authentication and account lifecycle

PR #2 is merged at `248917192c9d118c9e2ff3630a9e530a3e1c630a`. AUTH-04 is implemented on `feature/m1-auth04-account-activation`; test/CI evidence is in the canonical handoff. AUTH-05 onward remain pending. Do not reuse the former browser branch or merge this increment without owner authorization.

The first increment has health/token/tenant/provisioning foundations. This separate increment implements the following bounded work, in dependency order. All records and notification transports used in tests are synthetic/local. No paid SMS, production email or new infrastructure is required.

| Task | Depends on | Implementation and acceptance criteria |
|---|---|---|
| AUTH-01 Contract and browser integration spike | Reviewed foundation | Read architecture v1.1 section on browser auth and target OpenAPI. Demonstrate Sanctum stateful middleware with Edu-only, host-only HttpOnly Secure session cookies; exact trusted web origins; credentialed CORS; DB-backed sessions. Test allowed origin and denied sibling/Nursery/untrusted origins. Cross-site cookie architecture is a separate decision, not a reason to broaden the cookie domain. |
| AUTH-02 CSRF and Next.js session client | 01 | CSRF handshake and token delivery only to an exact allowed frontend origin, including host-only API cookie constraints. Central Next.js credentialed API client, generic error envelopes, private no-store responses and no bearer/session secrets in localStorage, URLs or generated HTML. Role shells render protected data only after server-authorized API response. Test missing/wrong CSRF, hostile Origin, preflight, logout and cross-subdomain behavior. Do not assume Next SSR receives an API-host-only cookie. |
| AUTH-03 Browser login and school context | 01–02 | Assigned identifier plus school code; active identity/membership/school required. Rotate session ID on login and privilege/context change. Never union roles across schools. Device school capability and browser school context are distinct mechanisms. A/B isolation, disabled membership, suspended school, role injection and cross-school session requests must fail. |
| AUTH-04 Activation and provisioning handover | 03 | Profile creation remains separate from SA-controlled account provisioning. Bind activation to school, membership, purpose and current provisioning authority; hash random single-use secrets, baseline 30-minute expiry, consume under lock and force password set. Tests cover replay, expiry, wrong tenant, changed authority and Principal denied provisioning/activation. No unvalidated profile-less student/guardian login creation. |
| AUTH-05 Recovery | 03–04 | Follow approved recovery contract, verified contacts or authorized assisted process. Generic responses for unknown/ambiguous/shared contacts; scoped throttling; hashed expiring single-use proof. Faked transport only. Reset atomically rotates credentials and revokes all device tokens, browser sessions and outstanding proofs; concurrent replay tests. Never use DOB/default passwords or plaintext recovery exports. |
| AUTH-06 Privileged MFA | 03–05 | Authenticator-based privileged baseline, with mandatory platform identity separation. Enrollment/reconfirmation, encrypted TOTP secret, one-time hashed recovery codes, bounded challenge attempts and expiry. Privileged actions unavailable before challenge completion. No SMS dependency. Test wrong/replayed/expired challenge, recovery-code replay, enrollment takeover and forced-password-change bypass. |
| AUTH-07 Session/device revocation | 03–06 | Staff browser inactivity 30 minutes; parent/student 8 hours; absolute 12-hour browser cap. Device baseline 7 days, privileged 12 hours; no custom refresh protocol. Revocation on logout, password/identifier/membership changes, expiry/suspension. List devices without exposing tokens; revoke one/all with ownership checks. Lock order consistent with provisioning/credential rotation. |
| AUTH-08 Permission and safety regression | 03–07 | Last active SA mutation serialized; school-specific bounded delegation and audit. Negative tests for forbidden powers, stale authorization, cross-school device/session use, changed guardian links, provisional states and expired entitlement. Academic modules remain out of scope. |
| AUTH-09 Mobile integration preparation | 03–08 | Document school-scoped token/error DTOs, reauthentication/revocation and OS secure-storage adapter contract. Mock API tests only until real mobile authentication is authorized in scope. No secrets in shared preferences/logs; no embedded server secret. Keep the safe Flutter CI boundary. |
| AUTH-10 Review and handoff | All above | Current-head CI on MariaDB, actual browser integration tests and safe Flutter checks; update contracts/migrations/ADR/status with exact evidence. No automatic merge/deploy. Separate review of privileged flows before real users. |

Do not treat account activation/reset/MFA as complete because a route or schema exists. Their acceptance gate includes replay/concurrency/negative tests and actual browser cookie/CSRF integration. Preserve Demo 30 days/zero files, Free 5 MB/50 PDFs/10 per day/500 MB, configurable paid policy and disabled student homework uploads unchanged.
