# Authentication increment 2 — implementation contract addendum

This addendum records the implemented AUTH-01–03 browser subset below and the pending lifecycle requirements. The approved target remains `packages/contracts/openapi.json`; `m1-implemented.openapi.json` records the earlier device/tenant foundation. AUTH-04 activation is implemented below; assisted recovery and bounded School Admin browser MFA are implemented in the addenda below.

Browser sessions use Sanctum stateful authentication, an Edu-only host-only API cookie, exact credentialed CORS and verified CSRF. Return a CSRF token only to a trusted origin where host-only cross-subdomain cookies cannot be read. Never widen the cookie domain to include Nursery. Missing/untrusted Origin and missing/invalid CSRF fail closed on browser mutations. Browser session rotation and logout revoke server-side state. Next.js must not infer school authority from its route name or accept tokens in URLs/localStorage.

Device school login now issues only `school:<school ULID>` capability. Tenant requests also require `X-School-ID`, current membership/role, school access and resource scope. A token issued for school A cannot be reused for school B even by a multi-school user; login/context authorization for B is separate. `TOKEN_SCHOOL_MISMATCH` is 403. Foreign resource IDs within an authorized context remain 404. Platform health requires an explicitly provisioned `platform:admin` capability, global platform identity and no forced password change. School login cannot issue platform tokens. No public platform token issuer exists in this increment.

Activation/recovery proofs must bind subject, school/membership, purpose, expiry and single-use state. All proof consumption is atomic; secrets are hashed at rest, never returned in account lists or logged. Recovery responses must not reveal contact existence or resolve a shared phone to the wrong identity. Student login remains possible without email. A Principal may create an admission profile but cannot provision or activate a login.

Successful password reset or identifier change revokes sessions, device tokens and outstanding lifecycle proofs. Logout and account security operations are narrow security exceptions to school read-only entitlement, with explicit authorization. MFA challenge completion precedes privileged authority. All responses retain request ID, generic error envelope and no-store; exception responses retain required protocol headers such as Allow and Retry-After.

Synthetic transport adapters and fake mail are sufficient for implementation tests. Real delivery, paid SMS and production origins/secrets are not authorized. The task dependency and acceptance matrix is in `docs/milestones/M1_AUTH_INCREMENT_2.md`.

## AUTH-01–03 implementation checkpoint

Browser routes use `/api/v1/browser`: GET `/csrf` returns a session-bound CSRF token only to an exact configured Origin; POST `/login` accepts school_code, identifier, password; GET `/me` resolves the authenticated role/school; POST `/logout` invalidates the session. Sanctum authenticates the browser web guard; device endpoints remain separate. Browser routes reject Authorization headers and require exact Origin even for reads. Cookies are encrypted, host-only, Secure, HttpOnly and SameSite=Lax. Only explicitly configured same-site Edu web/API HTTPS origins are supported; third-party cross-site hosting is not supported.

Use `EDU_BROWSER_ORIGINS` on the API and `NEXT_PUBLIC_EDU_API_BASE_URL` on web. Empty origin configuration denies access. CSRF is required even with same-origin fetch metadata. Login rotates session ID/token; staff idle expiry is 30 minutes, family 8 hours, absolute expiry 12 hours. Current membership, school access and credential hash are rechecked on every current-user request. Platform login and forced-password-change accounts are denied pending activation/MFA flows. AUTH-04 below adds first-time activation; later addenda define the implemented assisted recovery and browser MFA subset.

The Next.js client uses in-memory CSRF and credentialed fetch; no authentication material in localStorage. Protected role shells wait for `/me`; academic records remain unconnected. Real HTTPS browser tests run against MariaDB CI using web.edu.test and api.edu.test, synthetic fixtures, and transient test certificates. No production TLS bypass is configured.

## AUTH-04 implemented activation subset

See `packages/contracts/m1-activation.openapi.json`. All three endpoints use the existing `/api/v1/browser` HTTPS, exact Origin, credentialed cookie and CSRF boundary. `POST /accounts` requires current School Admin browser membership plus Idempotency-Key and accepts existing staff provisioning fields (teacher/principal only). It creates a pending activation account and returns membership_id, activation_status, replayed and a one-time `local_handover` only to that authorized issuer. Idempotent replay never returns a secret or reissues a proof. `POST /accounts/{membership}/activation/reissue` accepts an empty body, requires current School Admin authority in the same school, invalidates prior proofs, and returns a new local handover. Completed accounts cannot be reissued as a recovery shortcut.

The synthetic/local delivery adapter returns `{proof_id,secret,expires_at}` in that narrowly authorized School Admin response in local/testing only. It writes no plaintext proof to database, disk, logs or queues. Production issuance fails closed with 503 and transaction rollback until a separately authorized delivery adapter exists; no SMTP/SMS/WhatsApp is configured. No listing endpoint exposes proofs. Handover is for the intended account holder; never cache or export it. No initial password is returned by these new endpoints.

`POST /activation/consume` accepts school_code, proof_id, secret, password and password_confirmation. Anonymous possession of the intended one-time proof is required; a signed-in unrelated identity is rejected. Successful activation returns `{activated:true,login_required:true}`, consumes the proof atomically, finishes password setup, clears activation_required/must_change_password, revokes previous tokens/sessions, records audit, and rotates the anonymous browser session. It does not authenticate automatically. Invalid/expired/consumed/unavailable proofs share a generic 422 response; password/payload validation also returns 422. Baseline expiry is 30 minutes; secrets are 256 random bits, SHA-256 hashed at rest, purpose/user/school/membership bound. Reissue and consumption serialize on the school, then lock identity/membership/proof rows. Current write entitlement, issuer authority, target state and fingerprints are rechecked under locks. Model security mutations permanently invalidate pending proofs even if authority is later restored. Query-builder mutation paths must explicitly invalidate proofs; no such identity/role mutation API is introduced here.

New pending proof accounts cannot bypass activation through device login/password change or inconsistent browser flags. Existing activated-account device authentication remains compatible. Legacy POST /api/v1/accounts now delegates through the same activation-enforcing ProvisionStaff service; new provisioning never returns one_time_password, all new staff require proof consumption, and production issuance rolls back without delivery. This intentional provisioning-response security correction removes the former bypass; native Flutter proof consumption is not shipped. Future Flutter integration should use an approved activation transport and the same service contract, never reuse a school bearer token as activation proof. Student/parent provisioning remains closed pending validated profiles/guardian links; Principal admission profiles confer no account authority. No AUTH-05/06 workflow is introduced.

## AUTH-05 implemented assisted recovery subset

AUTH-04 merged at `ed7268a18266c0dd19dcf1dfe1004874023aba8e`. All recovery endpoints retain the browser HTTPS, exact Origin, credentialed CORS, host-only Secure HttpOnly cookie and CSRF boundary. No real delivery is enabled.

- `POST /api/v1/browser/recovery/request`: `{school_code,identifier}`; identical 200 message for every syntactically valid known/unknown/ambiguous/unverified identity. This implementation performs no identity/contact lookup and issues no proof. Current schema has no verified-contact evidence; automated verified-email recovery is deferred until that infrastructure and authorized delivery exist. Never infer verification from an identifier/phone or invent contacts. UI explicitly states no message was sent.
- `POST /api/v1/browser/accounts/{membership}/recovery`: current School Admin only, same school, another activated active nonplatform identity. Body: `{verification_method:"in_person_registered_record",verification_reference:"<opaque case reference,16–80 ASCII letters/digits/_/->",identity_verified:true}`. Before authorizing, the admin must verify the holder **in person against existing registered school records** and record evidence in the restricted school case register. Name, DOB or shared phone possession alone is insufficient. API records method, verification time, reference hash and current issuer; it cannot independently attest to the human check. Do not submit documents or personal details. Principal/Teacher cannot authorize. Reissue requires the same verification and current authority and invalidates outstanding subject recovery proofs. Self-assisted reset is denied; another authorized SA is required. Missing activated SA recovery authority requires a future separately approved process, never platform bypass.
- Authorized issuance returns `{local_handover:{proof_id,secret,expires_at}}` only in local/testing to the issuing admin. No plaintext persistence, list/export/log, real email/SMS/WhatsApp. Production issuance fails 503 and rolls back; previous proof remains intact. Use ephemeral synthetic handover only.
- `POST /api/v1/browser/recovery/consume`: `{school_code,proof_id,secret,password,password_confirmation}`; same password bounds as activation (12–72 characters, maximum 72 bytes). No proof in URLs or localStorage. 256-bit random secret hashed SHA-256 at rest, distinct password_recovery purpose/table, 15-minute expiry, single-use locked consumption. Invalid/expired/replayed/wrong-school/unavailable proof has the same generic 422 error. Signed-in unrelated identity is rejected. Pending activation/forced initial password setup, inactive user/membership, platform and suspended/archived school are denied; recovery never clears activation flags. Expired school write entitlement alone does not block this security operation.

Consumption serializes school → sorted identities → memberships → proof, revalidates current issuer/subject fingerprints, writes hashed password, consumes proof and revokes all user device tokens/browser sessions plus outstanding activation/recovery proofs (including proofs issued by that identity) atomically with append-only audit. Response `{reset:true,login_required:true}`; browser session is invalidated, CSRF rotates, and explicit sign-in is required. Model password/status/role/identifier/security changes permanently invalidate dependent pending recovery proofs; query-builder mutation commands must do so explicitly. No identity mutation API is introduced here.

Rate limits: public request and consumption 5/minute/IP in separate namespaces; authenticated assisted endpoint 5/minute/IP; service issuance 10/15 minutes/current issuer and 3/15 minutes/target membership; service redemption 5/15 minutes/school+proof ID. Throttle counters persist independently of rolled-back issuance and contain no raw proof/contact. Failures never partially change credentials/proof/audit state. UI pages `/forgot-password`, `/reset-password`, `/assisted-recovery`; proofs are in memory only, not analytics/URLs/storage. MFA, full device management, real delivery and verified-contact infrastructure remain outside this increment.

## AUTH-06 privileged browser MFA checkpoint

`/api/v1/browser/security/mfa`: GET `/status`; POST `/enrollment`, `/enrollment/confirm`, `/challenge`, `/recovery-code`, `/recovery-codes/regenerate`. All retain HTTPS, exact Origin, host-only cookies, CSRF, Sanctum and current BrowserSession checks. School Admin only; no public platform issuer. POST bodies allow only password (max72), plus code (max32) for confirmation/challenge/recovery. Status returns enrolled/verified, assurance_seconds=900 and server challenge deadline. Setup returns ephemeral secret/otpauth_uri/expires_in=600 to the authenticated holder only. Confirmation requires password plus TOTP and returns one-time recovery_codes and rotated csrf_token. Challenge/recovery also require password and the five-minute login challenge context; response verified plus rotated csrf_token. Regeneration needs current assurance plus password and invalidates the previous code set.

Login/current-user return mfa_required for School Admin; login routes to `/profile/security`. Pending sessions can access minimal identity/MFA bootstrap/logout, never provisioning, reissue or assisted recovery issuance. Service-level SchoolAccess.requireAdmin also enforces assurance. Public proof consumption remains distinct and does not depend on the issuer's current browser session. Legacy device provisioning and platform health return 403 until safe privileged transport exists; capabilities alone never establish MFA. Existing ordinary activated-account device login remains available. Password recovery preserves MFA enrollment. Reset/replacement of enrolled seeds remains unavailable.

Ten MFA mutation attempts per user per five minutes, password check under locks, 15-minute school/session/credential-bound assurance, ±30-second drift, strict TOTP replay counter, hashed once-only recovery codes. No client-provided MFA state or clock is trusted. See ADR-022 and the canonical handoff for current execution evidence. Session inventory, delegation and Flutter integration are subsequent phases on the same branch/PR, not claimed by this checkpoint.

## AUTH-07 session/device checkpoint

Browser GET `/api/v1/browser/security/sessions` and `/devices`; POST `/sessions/{id}/revoke` and `/devices/{id}/revoke`, body `{password}` only. `id=others` revokes other owned contexts. Browser inventory is identity-wide (maximum100 recently active records); devices are scoped to the current school. IDs are keyed opaque references, never raw session IDs/token values. Session inventory shows current and last activity; original start/absolute-expiry timestamps are not indexed and are explicitly null, not fabricated. Device inventory shows safe name/issued/last-used/expiry/current metadata. Sensitive mutations require password reauthentication; School Admin also needs current MFA. Exact Origin/CSRF/HTTPS/current-context checks are unchanged. `POST /api/v1/security/devices/{id}/revoke` and GET `/api/v1/security/devices` support ordinary device tokens through the existing active identity/tenant guards; privileged device management stays closed without browser MFA.

Revocation is serialized on school→identity→membership, owner-checked, auditable and excludes other users/foreign-school devices. A session revocation tombstone prevents an in-flight session handler from resurrecting authority by re-writing a deleted row. Password/security identity changes revoke tokens/browser contexts. Membership role/status/identifier changes revoke school-scoped tokens and conservatively all browser contexts belonging to that identity because the sessions table lacks indexed school metadata; no unrelated user's sessions are touched. Browser tombstones are checked by middleware and MFA/service assurance. Password recovery still keeps MFA enrollment and invalidates old credential-bound assurance. Ordinary device issuance is seven days; School Admin device issuance is twelve hours with privileged actions still closed. No refresh-token protocol.

`/profile/sessions` lists actual records and provides password-confirmed revocation controls, explicit user confirmation and safe expired/denied states. The existing staff/family idle limits and twelve-hour absolute browser lifetime remain authoritative. Complete multi-process issuance/revocation acceptance and the remaining AUTH-07 matrix must be confirmed before declaring the whole phase complete; capability delegation, last-admin mutation service and mobile client remain subsequent work.

## AUTH-07 completed supported lifecycle and AUTH-08 permissions

Active device inventory excludes expired and null-expiry credentials. Security model mutations and issuance use database transactions; school → identity → membership ordering serializes device issuance and membership changes. User credential updates include observer revocation and actual SQL update atomically. Independent-process MariaDB tests cover credential rotation versus issuance, membership revocation versus issuance, two owned-device revocations, and session revocation versus a protected request followed by a late session writer. Revoked rows cannot restore authority on a subsequent request. Exact staff/family idle and absolute limits have positive/negative middleware assertions; HTTPS tests cover actual server sessions and MFA cookie rotation.

GET `/api/v1/browser/security/permissions` returns `{school_id,registry,memberships:[{id,role,status,version,assignments:[{capability,allowed}],effective}]}` to a current same-school School Admin with current MFA. POST `/permissions/{membership}` accepts only `{capability,allowed,version}`; unknown names/extra input denied, stale version409, foreign membership404, unauthorized403. Mutation requires live write entitlement, current target eligibility, no self-grant and recipient ceiling. It atomically increments permission_version and appends before/after/version audit details. Revoke requires the same authority; every subsequent evaluation reads the current assignment and role, so cached sessions/tokens cannot retain a revoked grant. No client-provided school or actor authority.

Registry: `admission.profile.manage`, `financial.export`, `certificate.issue` for Principal; `marks.enter` for Principal/Teacher. These reserve future module boundaries; no academic/finance domain workflow is implemented. GET `/capabilities/{capability}/probe` is explicitly synthetic and returns `{authorized:true,synthetic:true,domain_implemented:false}` only after current authorization. Unknown/forbidden powers deny; Demo denies file-generating/export capabilities, write capabilities deny expired entitlement. Provisioning, activation, other-user recovery, permission assignment, platform powers, last-admin override, attendance correction and quota/safety overrides are never delegable.

`MembershipSecurity.change` is an internal, versioned, School Admin+MFA, school-locked role/status command with audit and rollback. Membership model updates independently protect last eligible active SA demotion/status removal; membership deletion is unsupported and denied. Two simultaneous removals serialize on the school row. Inactive, unactivated, password-setup or platform identities do not count as eligible backup administrators. Creating initial bootstrap membership is separate. No public bulk membership/global-identity administration route exists. Direct privileged SQL/query-builder administration is outside this application command boundary and can bypass model guards; future global-identity/bulk administration must acquire all affected school locks, preserve last-admin eligibility, revoke security contexts and audit. Do not introduce such a path by calling a raw update from a controller.

## AUTH-09 mobile contract and explicit persistence dependency

`POST /api/v1/auth/login` retains existing fields and adds server-derived `school_id,membership_id,user_id,role,abilities`. Exact one capability `school:<school_id>`, bounded expiry, activated identity and current school membership remain authoritative. `/me`, `/schools/{id}`, `/auth/logout` are existing device endpoints. No browser cookie/CSRF exchange is used by native tokens. No refresh endpoint exists. Password recovery/activation still require sign-in afterwards and revoke existing credentials; privileged device MFA remains unavailable.

Flutter now maps those DTOs, uses HTTPS-only bounded no-redirect JSON transport (explicit loopback-only local HTTP option), scoped Bearer/X-School-ID, in-memory identity and safe failure states, expiration timers, logout cleanup and fresh login on school change. Restored credentials require actual `/me` membership/role and scoped school revalidation. Tokens/proofs never enter URLs, logs, analytics or SharedPreferences. Production `PlatformSecureTokenStore` is a fail-closed MethodChannel adapter: there is no installed Android/iOS handler in this source-only scaffold. Missing/read/write/clear failure prevents authentication; tests inject a memory fake only. Native persistence and actual device/emulator verification are **NOT IMPLEMENTED/NOT RUN**, not production-secure storage. No native build or live mobile API test is claimed. The supported source/test integration can be reviewed independently of that explicit dependency.

Identity model security changes that remove eligibility (inactive status, platform flag, pending activation or forced setup) now lock all current active-SA schools in ID order before the identity and memberships, and apply the same last-admin guard before the actual update. Password-only rotation retains its existing identity lock. Independent MariaDB races cover identity deactivation versus deactivation and versus membership demotion. Initial bootstrap remains separate; no global administration API is added.

## SEC-02 synthetic platform browser subset (testing only)

Application configuration remains `platform.synthetic_auth=false`; production/staging issuer is unavailable even if configuration is changed because every platform service/policy also requires APP_ENV=testing. No public registration/operator bootstrap exists. The separate `scripts/platform-browser-router.php` disposable CI server enables the synthetic subset only for CLI-server, loopback requests and the `edu_test` database. It is never loaded by the public application entry point. Browser fixtures are CLI-only and satisfy the same environment/database restriction. Production-denial HTTPS tests use the ordinary public entry point with APP_ENV=production.

Under `/api/v1/browser/platform`, all routes retain exact trusted Origin, HTTPS, host-only HttpOnly Secure SameSite=Lax database sessions, CSRF for POST, no-store and no Authorization/X-School-ID substitution:

- POST `/login`: strict `{identifier:<user ULID>,password}`. Eligible activated global platform identity only. Rotates session/CSRF; returns `{mfa_required:true,csrf_token}` with a five-minute MFA deadline. Password success alone grants no capability.
- GET `/status`: current pending platform identity/context; returns `{user_id,enrolled,verified}`. Credential/session/revocation/absolute and idle checks remain active.
- POST `/mfa/enrollment`: `{password}`; only a currently unenrolled eligible holder. Returns ephemeral `{secret,expires_in:600}`. Encrypted pending seed, no overwrite of a confirmed factor.
- POST `/mfa/confirm`, `/mfa/challenge`, `/mfa/recovery`: `{password,code}`. Actual TOTP/recovery verification, atomic replay protection/audit; confirmation generates eight one-time recovery codes. Returns `{verified:true,recovery_codes,csrf_token}`. Session rotates before a session/MFA-version/credential-bound 15-minute assurance is stored.
- GET `/identity`: current eligible global identity plus valid session-bound assurance required. Returns `{user_id,context:"platform",capabilities:["platform.health"]}` only. No school/student/billing access.
- POST `/logout`: destroys platform session, records revocation/audit, rotates CSRF. Returns `{revoked:true,csrf_token}`. A school browser context cannot use this endpoint to cross contexts.

Next.js `/platform` implements sign-in, pending enrollment/confirmation or TOTP/recovery challenge, protected identity, unavailable/expired/error states and logout. Setup/recovery data exists in component memory only, never localStorage, URLs or analytics. Synthetic enablement is server-side only; no client switch. SEC-03 replacement and independently verified lost-factor reset are not implemented by this subset.

## SEC-03 supported authenticator replacement

Authenticated School Admin routes: POST `/api/v1/browser/security/mfa/replacement/start` and `/confirm`. Synthetic platform equivalents: `/api/v1/browser/platform/mfa/replacement/start` and `/confirm`; testing-only production issuer gate is unchanged. All retain the existing browser transport, Origin/CSRF, authentication, session expiry/revocation and current school/platform eligibility checks. Services revalidate under school/user/membership/credential locks independently of controller checks. No actor/user/school IDs are accepted in the body.

Start accepts strictly `{password,method:"totp"|"recovery",code}`. Requires current password plus a valid existing TOTP or unconsumed recovery code, atomically advances/consumes its replay state and audits issuance. Returns authorized no-store `{replacement_id,secret,expires_in:300}`. One unexpired pending intent per user; concurrent/repeated starts return409 rather than silently overwriting a setup. Old authenticator stays active. Pending seed is encrypted and bound to user, context, current credential/MFA version, school membership fingerprint where applicable, and exact session hash. Expired intent may be replaced only with fresh password/factor proof.

Confirm accepts strictly `{password,replacement_id,code}` with a NEW authenticator TOTP. Rechecks all current bindings and expiry, atomically swaps encrypted credential/version, rotates all recovery codes, consumes the intent, revokes browser/device sessions and appends audit. Returns `{recovery_codes:[8 once-only codes],reauthentication_required:true,csrf_token}` after transaction success. Current session/assurance is destroyed; fresh password/MFA login is required, never implicitly authorized. Failure/expiry preserves existing factor and credential state; audit failure rolls back mutation and old-factor consumption. Confirmation replay cannot reissue codes. Setup and recovery secrets are memory-only in the UI and must be saved offline, never in URLs/browser storage/logs.

School security settings and `/platform` include the replacement form and once-only final-code handoff. AUTH-05 recovery continues to preserve confirmed MFA. Independent lost-factor recovery remains **BLOCKED**: no password-only, unverified-contact or hidden override endpoint exists. Real production platform authentication still requires separately approved operator provisioning; SEC-03 does not enable it.
