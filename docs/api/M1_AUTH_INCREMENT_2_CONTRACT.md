# Authentication increment 2 — implementation contract addendum

This addendum records the implemented AUTH-01–03 browser subset below and the pending lifecycle requirements. The approved target remains `packages/contracts/openapi.json`; `m1-implemented.openapi.json` records the earlier device/tenant foundation. AUTH-04 activation is implemented below; recovery and MFA are not running endpoints.

Browser sessions use Sanctum stateful authentication, an Edu-only host-only API cookie, exact credentialed CORS and verified CSRF. Return a CSRF token only to a trusted origin where host-only cross-subdomain cookies cannot be read. Never widen the cookie domain to include Nursery. Missing/untrusted Origin and missing/invalid CSRF fail closed on browser mutations. Browser session rotation and logout revoke server-side state. Next.js must not infer school authority from its route name or accept tokens in URLs/localStorage.

Device school login now issues only `school:<school ULID>` capability. Tenant requests also require `X-School-ID`, current membership/role, school access and resource scope. A token issued for school A cannot be reused for school B even by a multi-school user; login/context authorization for B is separate. `TOKEN_SCHOOL_MISMATCH` is 403. Foreign resource IDs within an authorized context remain 404. Platform health requires an explicitly provisioned `platform:admin` capability, global platform identity and no forced password change. School login cannot issue platform tokens. No public platform token issuer exists in this increment.

Activation/recovery proofs must bind subject, school/membership, purpose, expiry and single-use state. All proof consumption is atomic; secrets are hashed at rest, never returned in account lists or logged. Recovery responses must not reveal contact existence or resolve a shared phone to the wrong identity. Student login remains possible without email. A Principal may create an admission profile but cannot provision or activate a login.

Successful password reset or identifier change revokes sessions, device tokens and outstanding lifecycle proofs. Logout and account security operations are narrow security exceptions to school read-only entitlement, with explicit authorization. MFA challenge completion precedes privileged authority. All responses retain request ID, generic error envelope and no-store; exception responses retain required protocol headers such as Allow and Retry-After.

Synthetic transport adapters and fake mail are sufficient for implementation tests. Real delivery, paid SMS and production origins/secrets are not authorized. The task dependency and acceptance matrix is in `docs/milestones/M1_AUTH_INCREMENT_2.md`.

## AUTH-01–03 implementation checkpoint

Browser routes use `/api/v1/browser`: GET `/csrf` returns a session-bound CSRF token only to an exact configured Origin; POST `/login` accepts school_code, identifier, password; GET `/me` resolves the authenticated role/school; POST `/logout` invalidates the session. Sanctum authenticates the browser web guard; device endpoints remain separate. Browser routes reject Authorization headers and require exact Origin even for reads. Cookies are encrypted, host-only, Secure, HttpOnly and SameSite=Lax. Only explicitly configured same-site Edu web/API HTTPS origins are supported; third-party cross-site hosting is not supported.

Use `EDU_BROWSER_ORIGINS` on the API and `NEXT_PUBLIC_EDU_API_BASE_URL` on web. Empty origin configuration denies access. CSRF is required even with same-origin fetch metadata. Login rotates session ID/token; staff idle expiry is 30 minutes, family 8 hours, absolute expiry 12 hours. Current membership, school access and credential hash are rechecked on every current-user request. Platform login and forced-password-change accounts are denied pending activation/MFA flows. AUTH-04 below adds first-time activation; recovery and MFA remain closed.

The Next.js client uses in-memory CSRF and credentialed fetch; no authentication material in localStorage. Protected role shells wait for `/me`; academic records remain unconnected. Real HTTPS browser tests run against MariaDB CI using web.edu.test and api.edu.test, synthetic fixtures, and transient test certificates. No production TLS bypass is configured.

## AUTH-04 implemented activation subset

See `packages/contracts/m1-activation.openapi.json`. All three endpoints use the existing `/api/v1/browser` HTTPS, exact Origin, credentialed cookie and CSRF boundary. `POST /accounts` requires current School Admin browser membership plus Idempotency-Key and accepts existing staff provisioning fields (teacher/principal only). It creates a pending activation account and returns membership_id, activation_status, replayed and a one-time `local_handover` only to that authorized issuer. Idempotent replay never returns a secret or reissues a proof. `POST /accounts/{membership}/activation/reissue` accepts an empty body, requires current School Admin authority in the same school, invalidates prior proofs, and returns a new local handover. Completed accounts cannot be reissued as a recovery shortcut.

The synthetic/local delivery adapter returns `{proof_id,secret,expires_at}` in that narrowly authorized School Admin response in local/testing only. It writes no plaintext proof to database, disk, logs or queues. Production issuance fails closed with 503 and transaction rollback until a separately authorized delivery adapter exists; no SMTP/SMS/WhatsApp is configured. No listing endpoint exposes proofs. Handover is for the intended account holder; never cache or export it. No initial password is returned by these new endpoints.

`POST /activation/consume` accepts school_code, proof_id, secret, password and password_confirmation. Anonymous possession of the intended one-time proof is required; a signed-in unrelated identity is rejected. Successful activation returns `{activated:true,login_required:true}`, consumes the proof atomically, finishes password setup, clears activation_required/must_change_password, revokes previous tokens/sessions, records audit, and rotates the anonymous browser session. It does not authenticate automatically. Invalid/expired/consumed/unavailable proofs share a generic 422 response; password/payload validation also returns 422. Baseline expiry is 30 minutes; secrets are 256 random bits, SHA-256 hashed at rest, purpose/user/school/membership bound. Reissue and consumption serialize on the school, then lock identity/membership/proof rows. Current write entitlement, issuer authority, target state and fingerprints are rechecked under locks. Model security mutations permanently invalidate pending proofs even if authority is later restored. Query-builder mutation paths must explicitly invalidate proofs; no such identity/role mutation API is introduced here.

New pending proof accounts cannot bypass activation through device login/password change or inconsistent browser flags. Existing device APIs and legacy staff provisioning response remain backward compatible for existing clients; native Flutter proof consumption is not shipped. Future Flutter integration should use an approved activation transport and the same service contract, never reuse a school bearer token as activation proof. Student/parent provisioning remains closed pending validated profiles/guardian links; Principal admission profiles confer no account authority. No AUTH-05/06 workflow is introduced.
