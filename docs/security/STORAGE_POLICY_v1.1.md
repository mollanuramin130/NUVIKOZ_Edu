# Owner-confirmed storage and PDF policy — effective baseline v1.1

28 October 2026 • Authority: attached Gate2 correction instructions, Phases2–7. This supersedes prior demo upload policy. Unaffected master prompt requirements remain in force. Decimal units: MB=1,000,000 bytes. Engineering selections below are labeled BASELINE, not owner approvals.

An effective server-side grant binds a storage policy version; an explicit school override has higher precedence, except fixed demo/student/tenant safety caps.

## Absolute Demo boundary

Demo means data_stage != live (including approved schools awaiting conversion). Before accepting a body, reservation, import job or ingestion command, server resolves actual tenant/context and denies user-supplied file mechanisms with403 `DEMO_UPLOAD_FORBIDDEN`. This covers multipart, raw bytes, JSON/base64/data URI attachments, CSV/Excel import, URL fetch, chunked/resumable upload, logos/photos/proofs, device sync and jobs. No privileged Demo-role exception; a PSA acting within a Demo school cannot override it. Runtime policy is checked again when a queued job runs and when bytes would be committed. Remote ingestion and file imports remain disabled launch features, including Live, until separately scoped.

Non-file student/class/session/attendance/homework/marks/notices/timetable/teacher/fee-demo CRUD remains enabled under existing capabilities. BASELINE abuse caps (PSA adjustable within platform safety):100 student profiles,25 staff profiles,200 guardians,20 classes,40 sections,100 subjects,2 sessions,50,000 total business rows and50 MB measured logical DB budget per Demo. Count dependent rows/audit/outbox in DB monitoring; exact InnoDB per-tenant physical attribution is approximate, never guaranteed by a SQL row count. Estimate bytes conservatively and stop expensive writes at safety threshold; resource controls remain independent of uploads. Default60 requests/min identity,300/min tenant and10/min public registration IP,100 record mutations/day and5 on-screen report computations/day. Endpoint-specific auth throttles still apply; performance data may justify revision, audited. Lightweight basic dashboard reads do not consume report-computation quota.

Demo exports/system PDF rendering cannot create tenant-owned physical files, either synchronously or via jobs:403 `DEMO_FILE_GENERATION_DISABLED`. Show tabular report results and marks/fee demonstrations on screen; shared sample PDF previews cover document examples. Fee-demo transactions remain explicitly SIMULATED, never create legally operative paid receipts or platform entitlement. This is a conservative BASELINE satisfying zero unauthorized background file creation. No real mail/SMS/push dispatch from Demo; in-app notifications/approval workflows may be simulated within that school only.

No tenant-to-platform sample foreign key grants ownership. Log preview metadata minimally.

Conversion preview contains authorized real demo records, origin flags, row versions/conflicts and sample exclusions. Shared sample IDs/files never enter private document bindings. Retry same manifest/key returns prior outcome; stale preview409. Core school/guardian/academic history preserved. A policy decrease in Live keeps authorized reads; no automatic deletion.

## Counting, replacement, deletion and races

A user-uploaded PDF is classified by verified content, not extension or caller label. Every successful new uploaded PDF blob, including a replacement/new version, consumes one daily admission. Copy/move/reference-only actions do not become new uploads but cannot allocate unaccounted physical copies. Idempotent retry of the same operation consumes once. Rejected/quarantined file is not active or successful daily admission; provisional counters remain reserved until rejection cleanup, and all physical/quarantine bytes still count globally and against applicable school-byte budget. Malicious attempts still consume anti-abuse request budget.

Active PDF count = logical school document bindings whose current available version is a user-uploaded PDF and whose document is not lawfully retired. Several bindings to one uploaded object must reserve separate active slots; do not permit link/copy APIs to bypass the cap. Retained superseded versions do not add active slots, but **every retained physical version counts bytes until actual approved purge**. Replacing PDF with PDF reserves daily1, bytes of whole new blob, active delta0; replacing non-PDF with PDF requires active+1. At50 active PDFs, a valid same-document replacement can succeed if daily/bytes/size allow; a51st logical active PDF fails. Retiring an active document releases its active slot after authorized lifecycle commit, not retained bytes; restoring it requires capacity again. Version churn cannot evade daily/byte caps. No hard delete shortcut to discard retention or audit.

Lock order for every file admission: global budget → school storage counter → policy version → school-local daily counter → affected document. Reserve bytes, net positive active slots, daily admission and a bounded expiring reservation in one DB transaction, with idempotency. Enforce current verified size≤5,000,000 bytes for Free Live even for exactly5MB payment-proof PDFs; image defaults remain2MB and MIME/purpose gates apply. Storage proof fields never relax caps. HTTP/vhost request limits must exceed application max plus multipart overhead, but do not become the application allowance. Read/proxy byte limit enforced on streams as well as declared Content-Length.

Commit verifies actual bytes/MIME/quarantine safety, membership, stage, entitlement, feature, policy version and all counters. Policy changes/decreases during a reservation require re-evaluation; cancel or safely re-reserve rather than grandfathering stale capacity. Commit consumes reserved counters once; cancellation releases reservations but physical bytes only after cleanup verification. Failed jobs/leases reconcile; DB transaction crash cannot expose unaccounted available objects. Append immutable usage events and reconcile physical files vs metadata/counters regularly.

Daily date is server-derived school-local date at admission commit. Reservation stores IANA timezone/version/day. If midnight passed, move/reserve admission under new current day while holding counters; old reservations cannot grant excess next-day admissions. School timezone change during active windows is versioned; retain conservative prior-window admission counts until reset so it cannot reset allowance repeatedly. Client date/time ignored. Count successful commits plus pending reservations for admission checks. Use unique(school_id,local_date,timezone_policy_version) and school lock; timezone safety aggregator checks overlapping windows. Server date affects limits, never a client parameter.

Total school bytes include available user uploads, retained versions and private generated school documents; pending bytes reserved. Quarantined/temp bytes remain physical budget occupants until cleaned. Platform-issued subscription receipts use platform billing storage payer. Every user-uploaded proof uses school storage payer and follows the originating Live school size/count/day/total-byte caps; no user file can switch payer to evade the school-byte limit. Full school-byte quota permits text reference submission and external WhatsApp proof for manual PSA recording; dashboard proof uploads have no bypass reserve. Demo accepts text references/support contact only, never screenshots. This supersedes the old platform-funded upload exception. Expiry permits narrow Live renewal proof commands only if file caps still permit; never academic uploads.

Generated PDFs are provenance `system_generated`, never decrement user PDF count/daily budget. School-private generated objects still count school+global bytes; platform receipts count platform/global bytes. Prefer deterministic content+template-version cache keys, on-demand streams with bounded temporary storage and≤1 generation job/tenant plus five generations/day default for optional reports (PSA adjustable); critical verified receipt metadata persists and rendering retries never repeat ledger approval. Generated attachment duplication cannot be labeled a free upload. Demo generation blocked; only shared samples previewed. New rendered objects failing capacity return503/retry state while immutable receipt metadata survives. Backend alone chooses provenance/payer; clients cannot forge them.

## Policy versioning and UX

Immutable `storage_policy_versions` holds phase/type applicability,max_pdf_bytes,max_active_uploaded_pdfs,daily_pdf_uploads,total_bytes. Free initial version exact5,000,000/50/10/500,000,000; demo fixed0/0/0/0; Paid inherits or PSA selects positive explicit values. School `storage_quotas` references effective policy version plus optional school-specific override version. PSA-only change route validates positive finite values, before/after/reason, effective time and optimistic version; lower cap preserves data/readability. Numeric zero is explicit forbid, never unlimited; null inheritance only during policy resolution, never ambiguous enforcement. No staff override of fixed security caps.

API capabilities include uploads_allowed and reason; UI Demo says 'File uploads unavailable in Demo' with sample-library action; no picker/paste/import controls. Free Live shows per-file5MB,activePDF used/50,daily used/10,total bytes,80% warning and most restrictive reason. Paid shows resolved values and policy version. Web and Flutter use same API status, server error codes and view flows; never trust cached capability after stage/policy change. Private PDF preview/download checks tenant, resource, current guardian/staff scope and entitlement read rules, safe inline/attachment disposition, rate limit, no-store and sensitive-download audit. Existing authorized reads survive full quota/expiry; suspension/revoked permissions remain distinct.
